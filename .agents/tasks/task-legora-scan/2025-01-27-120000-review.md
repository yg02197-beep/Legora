# Repository inventory and knowledge coverage scan

Adds a `legora scan` command that collects git-tracked files via `git ls-files`, cross-references them against the existing knowledge store's evidence anchors, and classifies each file as covered, stale, or uncovered based on freshness checks. Results are grouped by directory ("module") by default or listed per-file, with human-readable and JSON output modes. The implementation is minimal — three new source files plus CLI/render wiring — and ships with 15 unit tests covering the core classification logic and CLI integration.

**Watch for:** Sequential freshness I/O for every referenced record scales poorly on large repos with many knowledge records (confirmed). The `UNKNOWN` freshness → "stale" mapping is a deliberate fail-closed policy but the user-facing output doesn't distinguish genuine staleness from uncheckable evidence (confirmed). No filtering of non-source files from inventory — binary assets, lockfiles, and `.agents/` metadata all appear in coverage counts (confirmed).

**Verdict**: APPROVED

## High-level view

The scan pipeline is a three-stage chain: inventory collection shells out to `git ls-files`, the coverage mapper joins that file list against the knowledge store's `activeEvidence[].filePath` references, and freshness results determine classification. A per-record cache prevents redundant freshness calls within a single scan, but the overall pattern is still O(records × evidence-anchors) filesystem reads before the cache warms.

The command integrates into the existing CLI dispatch table following the same `--json` / `--depth` flag-parsing convention used by `bootstrap` and `doctor`. The module concept is simply `path.dirname` of each file, which means root-level files land in a `"."` module and repos with scattered top-level files produce many single-file modules in the output.

Coverage semantics are fail-closed: UNKNOWN freshness maps to "stale" rather than a distinct status, so the user cannot distinguish genuine drift from uncheckable evidence without inspecting the knowledge store directly.

<details>
<summary>Issues (3)</summary>

1. **No inventory filtering** — `git ls-files` returns every tracked path including binary assets, lockfiles, and `.agents/` metadata. These inflate total/uncovered counts and dilute the signal. Consider an extension point or default exclusion list.
2. **Sequential freshness I/O** — Each knowledge record's freshness check performs synchronous-sequential file reads. On repos with hundreds of records, scan latency will grow linearly. A bounded-concurrency approach (e.g., `Promise.all` with a pool) would mitigate this.
3. **Stale vs. uncheckable indistinguishable in output** — Files classified "stale" because freshness returned UNKNOWN (no snippet) look identical to files that genuinely drifted. The `renderScanResult` output could surface this distinction, or the `ScanResult` type could carry a fourth status.

## Inventory collection via git ls-files

`collectRepositoryInventory` returns every tracked path without filtering — `package-lock.json`, images, `.agents/` task metadata all land in the inventory. For a coverage tool whose purpose is answering "what source does Legora know about?", unfiltered inventory inflates the denominator with files that knowledge records would never reasonably cover.

The function does not handle `git ls-files` failure (non-git directory, git not installed). `execFile` rejects with an error that propagates through `computeScanCoverage`, and the CLI command has no try/catch, so this surfaces as a crash with a stack trace rather than a user-friendly message.

## Sequential freshness and scaling

The freshness checks are fully sequential: the `for...of` loop in `computeScanCoverage` awaits each `checkKnowledgeRecordFreshness` call one at a time. The record-level cache helps when the same record covers multiple files, but not when many distinct records each need one check. For repos where hundreds of files map to dozens of records, serial filesystem I/O will dominate scan time.

## Module grouping edge cases

`path.dirname` on relative paths produces a `"."` module for root-level files. The `--depth` flag controls only whether the output renders modules or individual files; it doesn't affect the computation — both `modules` and `files` arrays are always populated in `ScanResult` regardless of depth selection. This means the full per-file list is always computed even when only the module summary is rendered.

## Exit code semantics

Unlike `knowledge status` which uses exit codes 3/4/5 to signal empty/stale/unknown, `scan` always exits 0 on success regardless of coverage ratio. Scripts cannot use the exit code to gate on coverage thresholds without parsing the JSON output.

## Test coverage gaps

Not tested: behavior when `git ls-files` fails (non-git directory), very large inventories, the `"."` module edge case for root-level files, or the interaction between `--depth file` and `--json` together.
